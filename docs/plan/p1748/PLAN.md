## 2. Conflicts and decisions

- C1 Base branch: worktrees made from 01150b5 lack operator_roles.py, choose_quality, canary.py, restart_guard.py. Every build task starts from current main.
- C2 Write tool: the write check compares the target path against the main project folder instead of the task worktree. A worktree path is refused as outside the task, and a relative path is resolved into the main folder. This hit almost every author. P0 fixes it first, applied by the operator.
- C3 Tabs: take REDESIGN's 7 fixed destinations, Ctrl+1..7 = Chat, Live, Runs, Notes, MCP, Accounts & workers, Settings. The visual spec's Plan view (route, proposals, scores) lives inside Runs. p1642's MCP-on-Ctrl+4 is superseded; old shortcuts stay as aliases. Reason: parity needs real Accounts and MCP pages; a single Ops tab would be overloaded.
- C4 Tokens: use the dark token table, including accent-fill #6A4BE8 from REDESIGN.md for buttons with white text (about 5.5:1). The light theme ships only if a contrast tool confirms 4.5:1 for all text.
- C5 Panel: resizable 400-640 px, default 480 (visual spec). REDESIGN's 720 is rejected because the panel would cover too much page.
- C6 MCP: B3 is split. Data and actions are DIRECT (D1, D2); the view is part of the TEAM redesign (X6) and ports overlay.js loadMcp/renderMcp. If p1642 task tb2cfee1d merges first, D1/D2/X6 keep only what is still missing.
- C7 B4 and the MCP switch: there is no mcp_toggle action. The built-in switch calls settings_set with the row's toggle field (rea_enabled, roblox_enabled, blender_enabled, codebase_memory_enabled); local_mcp.public() already returns that field and page_settings_keys allows these keys (notion_shell.py:668-675). Custom servers already have an enabled flag (mcp_servers.py:32, and connect skips disabled ones at mcp_servers.py:50), but no route changes it today, so that switch is open item O1, not part of D2.
- C8 Bootstrap: the router cannot route its own build. Phase A and the first direct fixes (D1, D2) are routed by hand. From R7 on, the router decides live; every route label in this plan becomes an extra labelled row for the replay.
- C9 The quality canary runs once at the end (X10), not per task.
## 3. Task list (dependency order)

Rules for every task: start from current main; DIRECT = one build task + independent review by a different coworker + up to 2 fix rounds + machine check; TEAM = proposers, cross-scoring, one lead merge, then build/review/fix. Tasks in the same wave (section 4) run in parallel and share no file. Each task ends with RESULT: DONE or RESULT: NOT DONE: <reason>. Every task has a route, a Depends on line and a test file or a named smoke check.
